# iDrive bridge

This PluginApp registers one `App Manager` menu entry. It is the
only iDrive plugin NBT Manager needs: managed applications do not ship their
own. The manager's main menu starts them; holding the push on one opens its
settings, declared in its signed package, and stops it (see `PROTOCOL.md`).
Applications that need more from iDrive (car data, the focus hold while they
are shown) are to get it through the bridge, the documented car interface
designed in `docs/app-bridge.md`, implemented by this plugin and the worker. Selecting it
spawns the fixed executable `/var/opt/nbt-manager/manager/nbt-manager-launcher`
with the sole argument `--open`, and holds iDrive's focus on an inert state while
the manager window is shown (see `docs/controller-input.md`, "iDrive focus
hold"). When a manager GUI is already running, selecting the entry brings its
window back instead of spawning. It starts the launcher as NBT-AAD starts its
daemon: QNX `spawn()` with a descriptor map, its own process group, default
signal actions, an empty signal mask, and NBT-AAD's `PATH` followed by the
HMI's environment without its `PATH` (`include/nbt/process/hmi_environment.hpp`).
No shell, no HMI descriptors, a non-zombie child. The launcher starts the
worker and then the GUI the same way (`src/process/child_spawn.cpp`), passing
its environment on and giving each one end of their private channel.
Failure to start is reported to QNX slog; success means the process was spawned,
not that a GUI opened. When `/var/opt/nbt-manager/manager/debug.log` exists
(checked at each selection), the plugin also appends its selections, focus
changes and hold actions to it (`src/log/log.cpp`, without rotation; see
`docs/bench-checklist.md`). The HMI process must be able to write that file.

Focus events (`triggerEvent`) are sent from the plugin's own `nbt focus`
thread (`focus_events.cpp`, `src/gui/focus_sender.cpp`), never from the
iDrive thread that runs its callbacks: iDrive answers them synchronously with
no timeout. When one is not answered within 3 s, the `nbt focus watch` thread
writes every HMI thread to the debug log (`hmi_threads.cpp`), again at 10 s,
and the plugin drops the hold, so iDrive can never be left frozen behind a
focus event.

The launcher verifies a provisioned manager slot, supervises the GUI and worker,
and recovers an interrupted candidate trial. A managed lock prevents repeated
selections from opening another window while one is active. If the GUI dies, the
plugin's bounded liveness check releases the focus hold instead of waiting for a
stale lock. The preview shows worker startup status and closes after 45 seconds.
The desktop installer provisions the manager and stages manager updates.

`NbtManager.manifest` references the XML and generated image and text ZIPs.
`make qnx-plugin RHMI_LIBDIR=/path/to/libraries` produces the complete bundle in
`build/NbtManager/`. It needs local copies of `libAppFramework.A.so` and
`libCoreFramework.A.so` and the QNX 6.5 GNU C++ `_gpp` toolchain. Plugin-linked
code remains STL-free and performs no heap allocation. No BMW libraries are
distributed here. The menu icon and preview are generated by
`make_resources.py`.

The declarations, vtable layout and 0x200-byte storage are reconstructed ABI
assumptions informed by the existing AAD PluginApp and local framework
libraries. They match `libAppFramework.A.so` and BMW's own plugins in firmware
NBTevo_Y21432J (vtable slots, object size, `Runnable`, `pluginAppInfo`, delegate
layout; see `docs/head-unit-interfaces.md`), which is agreement with the
libraries, not runtime proof. The menu placement follows that reference. The
connector ID does not: each plugin has its own (firmware: ActiveSeating 17,
SecurityMenu 200; NBT-AAD 210). Sharing NBT-AAD's 210 makes the entry's focus
events do nothing and stops Android Auto, so the manifest uses 220. A
successful build is not proof that the plugin loads safely into `HmiMain3D`:
the bench checklist covers the ABI, placement, coexistence, action, process
launch, input and display clean-up. The desktop installer performs the initial plugin registration as
an explicit setup operation when the HMI filesystem is writable.


## Phone wake and door

The plugin keeps a one-second idle poll as well as the active hold poll. After 15 seconds it asks the launcher for `--door`; a shared-memory guard
allows three failed starts and re-arms after 60 seconds of healthy door
liveness. The launcher verifies and starts only the known-good slot's worker,
with a private readiness handshake, then releases its operation lock.

`phone_runtime.cpp` subscribes to `driving.speedActual` and
`hmi.graphicalContext`, and requests both once a second with the same delegates
because the subscription interval is a debounce limit. `framework.hpp` records
the three CDS add/get/remove ABI signatures, checked against the shipped
`libAppFramework.A.so` (SHA-256
`75aff211cfe29e904cdc8545bf8f4e9174c132dc0469e0a7ef84296391ada69f`).
Static inspection confirms the shared callback map and UTF-16 JSON value;
source freshness and runtime behavior remain car checks.

A signed wake creates a fixed private marker. Before calling the existing
entry/open path, the plugin checks Open from phone, zero speed received within
three seconds, the exact observed home context (3 / LT_Table_ID6L_Pad_Title)
and iDrive surface 256 alone on the panel. The display query is asynchronous
and bounded, so it does not block the HMI thread. Camera/unknown contexts and
Android Auto return busy; unknown/stale speed returns moving. Navigation wake
requires more car evidence. The car still owns every approval.

Wake/liveness/boot-counter records use the existing QNX shared-memory behavior:
0600 owned regular objects with the opened inode checked against the name;
QNX's natural 2/3-link report is accepted only under /dev/shmem. Persistent
trust/settings/lifetime-lock files remain under the central managed-root path
policy and retain the one-link check. No fsync/rename is assumed on shmem.
The lifetime lock itself is on the managed QNX6 filesystem.
